\# CLAUDE.md



\## О проекте

DupeFinder — веб-приложение для поиска дубликатов фотографий на большом

NAS-хранилище (ориентировано на Synology, но не привязано к нему жёстко).

Состоит из двух процессов на одном Python-коде: тонкого Flask-сервера

(`app.py`) для просмотра/ревью результатов и отдельного скрипта-сканера

(`scanner.py`), который запускается как detached OS-процесс через

`subprocess.Popen(..., start\_new\_session=True)`.



Ключевая архитектурная идея, повторяющаяся в комментариях по всему коду:

\*\*Flask никогда не сканирует сам и никогда не блокируется на тяжёлой

работе\*\* — он только пишет/читает SQLite и запускает/останавливает сканер.

Это даёт: не блокирующий UI при сканировании 270k+ файлов, устойчивость

прогресса к перезапуску Flask и разрыву соединения браузера, и дешёвую

реализацию Stop/Resume через простой флаг в БД.



\## Стек и зависимости

\- Python 3.12, Flask ≥3.0, Pillow ≥10.0, NumPy ≥1.24, SciPy ≥1.10

&#x20; (`requirements.txt`).

\- Опционально (`requirements-optional.txt`, best-effort в Dockerfile,

&#x20; `|| true` — сборка не должна падать, если wheel недоступен под архитектуру):

&#x20; `pillow-heif` (HEIC/HEIF) и `rawpy` (DNG/RAW). Без них такие файлы просто

&#x20; пропускаются с понятной ошибкой в `scanner.log`, приложение не падает.

\- Perceptual hashing (pHash) реализован \*\*вручную\*\* в `hashing.py` через

&#x20; `scipy.fft.dctn`, а не через пакет `imagehash` — комментарий в коде прямо

&#x20; объясняет: в среде разработки не было сетевого доступа для pip install

&#x20; этого пакета. Если предлагаешь рефакторинг — не заменяй это на

&#x20; `imagehash` без явной просьбы пользователя, это осознанное решение.

\- SQLite — единственное хранилище состояния (WAL-режим, чтобы читатель

&#x20; Flask не блокировал писателя-сканер).



\## Запуск и деплой

\- Локально: `python3 app.py` (порт 5000) при уже проинициализированной

&#x20; БД (`db.init\_db()` вызывается автоматически при импорте `app.py`).

&#x20; Сканер запускается вручную: `python3 scanner.py /path/to/photos

&#x20; \[--rotation-pass] \[--scan-id N]`.

\- Через Docker: `Dockerfile` на базе `python:3.12-slim`, ставит `tzdata`,

&#x20; требуемые и опциональные зависимости, копирует весь проект, задаёт

&#x20; `ENV DUPEFINDER\_DATA\_DIR=/data`, создаёт `/data` и `/photos`, открывает

&#x20; порт 5000, `CMD \["python3", "app.py"]`.

\- `docker-compose.yml` монтирует реальный путь NAS к фото 1:1 (левая и

&#x20; правая часть volume одинаковы, чтобы путь в File Station совпадал с тем,

&#x20; что вводишь в форме приложения) и отдельный volume для `/data` (БД, логи,

&#x20; кэш превью) — эти данные должны жить \*\*вне\*\* папки проекта, чтобы

&#x20; переживать `docker compose up -d --build`.

\- `DOCKER\_SETUP.md` — пошаговая инструкция именно для Synology Container

&#x20; Manager (GUI) плюс альтернативный путь через SSH + `docker compose`.

&#x20; Там же — рекомендация тестировать сначала на маленькой подпапке (пара

&#x20; сотен фото) перед сканом всей библиотеки.

\- Переменные окружения (все читаются в `config.py`, все с префиксом

&#x20; `DUPEFINDER\_`): `DUPEFINDER\_DATA\_DIR`, `DUPEFINDER\_TRASH\_DIRNAME`,

&#x20; `DUPEFINDER\_SMTP\_HOST/PORT/USER/PASSWORD/FROM`, `DUPEFINDER\_NOTIFY\_EMAIL`.



\## Структура кода и разделение ответственности

\- `config.py` — все настраиваемые константы и пути в одном месте: пути

&#x20; данных, исключаемые директории (`\_DupeFinder\_Trash`, `@eaDir` —

&#x20; синологовский кэш миниатюр), поддерживаемые расширения изображений,

&#x20; параметры pHash (`PHASH\_SIZE=8` → 64-битный хэш, `PHASH\_HIGHFREQ\_FACTOR=4`),

&#x20; порог совпадения `MATCH\_HAMMING\_THRESHOLD=8`, кадансы записи прогресса,

&#x20; параметры ETA, SMTP/уведомления, размеры превью.

\- `db.py` — вся схема SQLite и работа с соединением. Таблицы: `roots`,

&#x20; `scans` (статусы `running|done|error|stopped`, флаг `stop\_requested`,

&#x20; `rotation\_pass`), `files` (уникальность по `(root\_id, path)`, статусы

&#x20; `pending|done|error|trashed|missing`, хранит `phash` + три ротационных

&#x20; варианта, EXIF-даты как "лучшее предположение" и как "сырые", если EXIF

&#x20; реально есть), `scan\_progress` (текущее состояние прогресса на скан),

&#x20; `progress\_samples` (скользящее окно для ETA), `groups`/`group\_members`

&#x20; (результат кластеризации), `review\_state` (отметки reviewed/marked),

&#x20; `settings` (произвольные сохранённые настройки, напр. group\_by).

&#x20; `init\_db()` делает лёгкие миграции через `\_ensure\_column` — паттерн для

&#x20; добавления новых колонок в существующие установки без пересоздания БД;

&#x20; новые миграции нужно добавлять именно так, а не менять `CREATE TABLE`

&#x20; ретроактивно.

\- `hashing.py` — вычисление pHash: EXIF-ориентация нормализуется

&#x20; (`ImageOps.exif\_transpose`) до хэширования, так что поворот через

&#x20; EXIF-флаг не меняет хэш; поворот через реально перекодированные пиксели

&#x20; НЕ нормализуется по умолчанию (это дорогая операция — отдельный opt-in

&#x20; `rotated\_variants()`). `open\_any\_image()` — единая точка открытия любого

&#x20; формата, включая HEIC (через `pillow-heif`, если установлен) и DNG

&#x20; (через `rawpy`), с понятной `UnreadableImageError` вместо краша.

\- `cluster.py` — группировка файлов по похожести хэшей: BK-tree для

&#x20; быстрого поиска соседей по расстоянию Хэмминга + Union-Find для

&#x20; объединения в группы. `cluster\_files()` — первичная кластеризация по

&#x20; основному `phash`; `merge\_rotation\_matches()` — отдельный проход,

&#x20; который дополнительно сверяет ротационные варианты хэшей файлов, ещё не

&#x20; попавших ни в одну группу, и подмешивает их в существующие/новые группы.

\- `scanner.py` — весь жизненный цикл скана: `discover\_files()` обходит

&#x20; дерево, пропуская Trash и `@eaDir`; `sync\_file\_list\_to\_db()` делает

&#x20; upsert файлов (не трогает уже `done` файлы с тем же size+mtime — основа

&#x20; резюмируемости) и помечает исчезнувшие файлы как `missing` (важно для

&#x20; корректной сверки при импорте сохранённой сессии); `ProgressWriter`

&#x20; батчит записи прогресса (не чаще, чем раз в `PROGRESS\_WRITE\_INTERVAL\_\*`)

&#x20; и параллельно пишет историю для ETA; `is\_stop\_requested()` проверяется

&#x20; между файлами — Stop останавливается не мгновенно, а в пределах

&#x20; обработки одного файла, и уже нахэшированное всё равно кластеризуется и

&#x20; сохраняется как частичный результат; `run\_scan()` — оркестрация всей

&#x20; последовательности (discover → hash → cluster → optional rotation pass →

&#x20; write\_groups → notify).

\- `app.py` — Flask-роуты, разделены на группы:

&#x20; - страницы: `/` (список root'ов со статусом последнего скана),

&#x20;   `/review/<root\_id>`;

&#x20; - управление сканом: `POST /api/scan/start` (валидирует папку, создаёт

&#x20;   запись скана, запускает `scanner.py` как detached subprocess),

&#x20;   `GET /api/scan/progress/<scan\_id>` (прогресс + ETA, `\_calculate\_eta`

&#x20;   считает скорость по скользящему окну, до накопления

&#x20;   `ETA\_MIN\_SAMPLES` возвращает `"calculating"`), `POST

&#x20;   /api/scan/stop/<scan\_id>` (просто ставит флаг `stop\_requested`);

&#x20; - результаты: `GET /api/groups` — постраничная выдача групп дубликатов

&#x20;   с тремя режимами (`content`, `date`, `filename`), двухшаговая

&#x20;   пагинация (сначала считаем count по ключам группы в SQL, берём одну

&#x20;   страницу ключей, затем тянем полные строки только для них) плюс

&#x20;   защита `MAX\_GROUP\_ROWS=100` от аномально большой одной группы через

&#x20;   оконную функцию `ROW\_NUMBER() OVER (PARTITION BY ...)`; `GET

&#x20;   /api/summary` — сводные цифры (сколько групп, лишних копий, сколько

&#x20;   места можно освободить) — считается live, игнорируя фильтр "скрыть

&#x20;   просмотренные", чтобы оставаться честной метрикой; `POST /api/hide`

&#x20;   (пометить `reviewed`, обратимо), `POST /api/mark` (выставить

&#x20;   `marked\_for\_delete`/`reviewed` по одному файлу), `POST /api/delete`

&#x20;   (переместить помеченные файлы в Trash через `trash.move\_to\_trash`);

&#x20; - превью: `GET /api/thumb/<file\_id>`, `GET /api/full/<file\_id>` —

&#x20;   отдают JPEG через `preview.get\_preview\_bytes` независимо от исходного

&#x20;   формата; `GET /view/<file\_id>` — полноэкранный просмотрщик с

&#x20;   поддержкой навигации по группе через `?ids=1,4,7` (стрелки

&#x20;   влево/вправо между соседними файлами группы);

&#x20; - сессии: `GET /api/session/export`, `POST /api/session/import`.

\- `session\_io.py` — экспорт/импорт JSON-снапшота "что просмотрено/помечено",

&#x20; сознательно отдельно от основной SQLite БД (человекочитаемый, версионируемый

&#x20; файл). При импорте сначала сопоставление по `(root\_path, rel\_path)`, если

&#x20; файл переехал/удалён — fallback на сопоставление по `phash`; не

&#x20; сматченное не роняет импорт, а возвращается как предупреждение.

\- `trash.py` — перемещение в `\_DupeFinder\_Trash` внутри того же root'а

&#x20; (не системная корзина ОС), сохраняя относительную структуру папок.

\- `notify.py` — desktop-уведомление + опциональный email по SMTP при

&#x20; завершении/остановке/ошибке скана; при пустом `SMTP\_HOST` — только лог +

&#x20; desktop.

\- `preview.py` — генерация и дисковый кэш JPEG-превью (ключ кэша —

&#x20; `file\_id + mtime`, так что пересканированный/изменённый файл получает

&#x20; свежий превью автоматически); никогда не бросает исключение наружу —

&#x20; недекодируемый файл превращается в плейсхолдер-картинку с текстом.



\## Соглашения и то, что важно не сломать при изменениях

\- \*\*Не переносить хэширование/сканирование в `app.py`\*\* и не делать

&#x20; `scanner.py` зависимым от Flask — граница процессов — часть контракта

&#x20; надёжности (переживает рестарт контейнера/Flask-воркера).

- **Не менять пороги (`MATCH_HAMMING_THRESHOLD`, `PHASH_SIZE`) без понимания
  последствий**: увеличение `PHASH_SIZE` даёт более длинный хэш (64 бит при
  size=8), что означает, что тот же абсолютный порог Хэмминга соответствует
  более строгому относительному сходству и снижает число случайных
  совпадений по макроструктуре изображения. Если меняешь эти константы —
  делай это осознанно и проверяй на реальном наборе фото, а не только на
  тестовых данных.
- **Не убирать нормализацию EXIF-ориентации** в `hashing.py` перед основным
  хэшированием — иначе одинаковые фото, повернутые только через EXIF-флаг
  (частый случай со смартфонов), перестанут матчиться как дубликаты.
- **Ротационный проход (`--rotation-pass`, `merge_rotation_matches`)** —
  дорогая опциональная стадия, не включай её по умолчанию в UI без
  явного запроса пользователя: она пересчитывает дополнительные хэши для
  повернутых версий и увеличивает время скана.
- **Резюмируемость сканов держится на паре (size, mtime) в `files`** —
  любое изменение логики `sync_file_list_to_db()` должно сохранять это
  поведение, иначе повторный запуск скана на уже обработанной библиотеке
  начнёт пересчитывать всё с нуля.
- **Миграции только через `_ensure_column`** в `db.py` — не переписывай
  существующие `CREATE TABLE`, чтобы не терять данные на уже
  развёрнутых у пользователей инсталляциях.
- **`preview.py` никогда не должен бросать исключение наружу** — при
  добавлении новых форматов изображений сохраняй паттерн: недекодируемый
  файл превращается в плейсхолдер, а не в 500-ю ошибку Flask.
- **Флаг `stop_requested` проверяется между файлами, а не мгновенно** —
  это осознанный компромисс: не нужно городить сложную межпроцессную
  синхронизацию, а частично обработанный скан всё равно кластеризуется и
  сохраняет полезный частичный результат.

## Что стоит иметь в виду при доработках

Если тебя попросят добавить визуальную подсказку о качестве кластеризации
на странице ревью, разумный путь — показывать максимальное расстояние
Хэмминга внутри группы прямо в интерфейсе, чтобы можно было на глаз
отличить надёжные группы от подозрительных (с большим внутренним разбросом)
ещё до того, как доверяться автоматической группировке. Это не реализовано
сейчас, но вписывается в существующую архитектуру `cluster.py` без
структурных изменений.

Note по текущему состоянию: значение `MATCH_HAMMING_THRESHOLD=8` в
`config.py` было подтверждено при чтении файла ранее в этой сессии; если
с тех пор в код вносились правки, стоит перечитать константу перед тем,
как на неё опираться.
